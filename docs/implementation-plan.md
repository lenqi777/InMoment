# InMoment 产品与技术实现方案

版本：v0.4 建议稿｜日期：2026-10-16

这是早期设计稿，当前功能与操作见[使用指南](USER_GUIDE.md)，后续变化见[更新日志](../CHANGELOG.md)。

本次交互更新：首次长按右键触发并在按住期间录音，松开自动暂停；此后点击“继续录音”直接开始持续录音，由用户点击“暂停”来暂停。每次暂停提供“删除／继续录音／完成记录”。详细状态、误触处理及数据清理规则见 [录音交互与数据生命周期](recording-lifecycle.md)。

## 1. 建议采用的产品方向

首版采用 Windows 常驻桌面应用、本地保存、按用户触发采集的路线，建议先以 Windows 11 x64 作为验证与打包目标。浏览器扩展用于后续增强网页内容获取，不作为桌面录音和截图的前置条件。

首批验证场景收窄为：用户在电脑上阅读网页、聊天回复、PDF 或作品集时，留下突发联想；几天后能找到记录，并解释当时为什么记录它。

产品需要保存三类真实线索：看到了什么、自己说了什么、当时正在做什么。最后一项可以未知。帮助重建理解是产品目标，恢复当时的兴奋感不作为承诺。

建议把产品价值写为：

> 在灵感出现的现场，用语音留下个人联想，同时保留经授权的画面和来源线索；以后通过模糊描述找到记录，并回看当时的表达与情境。

## 2. 对原 README 的具体改进

1. **把“保存”拆为临时保管与正式记录。** 按住和暂停期间仅在本地保管草稿；用户点击“完成记录”后正式保存，再执行 AI 整理。断网或模型失败不能导致已完成的原始记录丢失。
2. **将必填项降至零。** 标题、分类、任务、项目均可为空；用户结束后仍可直接离开。首次系统权限设置单独完成。
3. **将触发与理解分开。** 截图证明捕捉到了某个画面，不证明用户正在研究某个问题；窗口标题也不能直接当作任务。
4. **将来源快照与浏览过程分开。** MVP 保存触发时的一次窗口快照，不声称记录了随后所有页面变化或完整思考过程。
5. **将原始表达、AI 整理、用户修订分开。** 每条整理内容可追溯到原话；修订摘要不覆盖录音。
6. **将回到主线分级。** 回看情境、切回窗口、打开来源链接、定位具体段落是不同能力，分阶段实现。
7. **首次按住录音，续录手动控制。** 首次达到长按阈值后录音，松开自动暂停；点击继续录音后直接持续录音，点击暂停才暂停。第一轮验证右键触发与原应用的兼容性；辅助快捷键不替代主要交互。
8. **说明图片检索的边界。** 第一版截图用于回看；检索依据来自转写、用户补充文字、任务及窗口信息。画面文字搜索需要后续 OCR 或图片理解能力。

## 3. 需求、交互与实现的对应关系

下表是建议验收方式，不是已有测试结果。

| 需求 | 用户如何使用 | 通过什么实现 | 验证什么 |
| --- | --- | --- | --- |
| A. 突发想法快速记录 | 首次长按右键录音，松开自动暂停；点击继续录音后持续录音，手动暂停 | 状态机区分首次按住模式与后续手动模式，复用同一草稿 | 首次短按不采集；首次松开暂停；手动模式不受右键松开控制 |
| B. 保留发生情境 | 语音同时关联原窗口信息与经授权的一张截图 | 先冻结活动窗口标识、应用名和标题，再捕获该窗口；分别保存触发和截图时间 | 没有截到 InMoment 自己；截图失败仍能录音；未知 URL 和任务保持未知 |
| C. 表达结束后整理 | 首次松开或后续手动暂停显示三个选项；点击完成后显示“已保存，整理中” | 完成前仅本地草稿；正式提交后执行 ASR、结构化整理与索引 | 暂停不调用 AI；删除清理全部草稿材料；模型超时不影响正式保存 |
| D. 无分类管理 | 默认进入按时间排列的收件箱；之后可修改标题、添加多个标签 | 灵感事件允许无标题、无标签、无任务；自动标题和标签只是草稿 | 不填写任何分类也能保存、播放和查找 |
| E. 模糊找回并理解 | 输入“之前那个收藏了却忘记原因的想法”，查看原话、画面和当时任务 | 中文关键词检索与语义向量检索合并；结果按事件聚合，展示命中片段 | 用几天后的自然描述找回目标，并能解释原始意图；不能只测复制原句 |
| F. 发散后回到主线 | 结束后按需查看“从哪里开始、谈了哪些分支”，或切回来源窗口 | 保存可选任务锚点与来源窗口；整理引用用户表达中的思路分支 | 不在录音中提醒跑题；任务缺失时不编造；窗口关闭时明确无法恢复原窗口 |

## 4. 一次完整使用流程

### 4.1 首次设置

- 用户明确开启麦克风与按次窗口截图功能；截图可以关闭。
- 验证长按右键的触发阈值和原应用兼容性；配置可选辅助快捷键并检查冲突。
- 说明云端 ASR、文字整理和向量生成各自会发送什么。未启用云端功能时仍能本地保存记录。
- 可排除特定应用或窗口。无法识别敏感内容时，不承诺自动防止所有误采集。

### 4.2 日常捕捉

1. 用户在浏览器、PDF 阅读器或其他应用中按住右键。未达到长按阈值便释放时，不采集截图或音频，不建立内容草稿。
2. 达到阈值后，Windows bridge 记录活动窗口的 HWND、PID、进程身份、窗口标题和时间，创建临时会话 ID。
3. 在确认右键仍按下时启动音频采集，并对原窗口异步截图；截图先于浮层显示，失败或超过等待预算也不能阻塞松开后的停止处理。
4. 首次按住期间显示录音状态；松开后立即请求停止当前音频段、释放本应用的麦克风流，并显示“删除／继续录音／完成记录”。不出现 AI 建议、分类要求或偏题提醒。
5. 点击“删除”后，使会话失效并清理所有临时材料；点击“继续录音”直接开启手动控制的持续录音，向同一草稿追加下一段，无须按住右键；点击“暂停”后再次显示三个选项。点击“完成记录”才将草稿提交为正式记录。
6. 正式保存成功且用户已开启相应云端处理后，后台依次转写、整理、生成索引；完成后不强行弹出大窗口。
7. 用户以后可以通过时间、应用、关键词或自然语言找回正式记录，并回看证据。临时草稿不进入搜索索引。

这里的“同时”是并行启动，不代表截图和录音具有同一物理时间戳。程序分别保存实际采集时间，避免把异步截图称为按键瞬间的画面。

## 5. 推荐技术路线

推荐使用 **Electron + React/TypeScript + 小型 C# Windows bridge + SQLite + 可替换的模型 API**。

这一路线面向快速完成可用原型：React 负责录音浮层、记录详情和检索界面；Electron 管理常驻生命周期；C# 仅封装必要的 Windows 原生能力。代价是需要打包两个运行组件，并实测常驻内存与安装包体积。

### 5.1 模块职责

| 模块 | 职责 | 实现建议 |
| --- | --- | --- |
| Electron 主进程 | 托盘、窗口生命周期、设置、权限策略、进程通信 | 主界面关闭时可继续常驻；正在录音时退出须先正常结束 |
| React 界面 | 悬浮录音状态、列表、详情、搜索、修订 | 使用窄范围 preload API；界面不能任意读写文件或执行系统指令 |
| C# Windows bridge | 全局鼠标按下与释放、可选快捷键、活动窗口元数据、单窗口截图、切回来源 | 输入处理与耗时任务分开；通过受限本地 IPC 通信；监听异常时优先停录 |
| 独立录音 renderer | 首次按住采集、松开暂停；后续点击续录、手动暂停 | getUserMedia + MediaRecorder；区分按住与手动模式；多段属于同一草稿 |
| 本地处理 worker | 音频落盘、SQLite、模型请求、检索计算 | 避免耗时处理阻塞界面和快捷键响应；任务状态持久化 |
| SQLite | 事件、来源、转写、整理、索引、处理任务 | 启用 FTS5，检查打包版本确实包含所需能力；附件放文件系统 |
| 模型适配层 | ASR、结构化整理、Embedding | 第一版调用现成 API；独立替换服务商，不自行训练模型 |

Electron 的主进程、renderer 与 utility process 支持这种职责划分；这是基于其能力作出的架构选择。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)

### 5.2 为什么仍需要一个 Windows bridge

Electron 能处理常驻和交互，但本项目需要稳定获取其他应用的前台窗口身份，并围绕同一窗口截图与返回。把这些操作放在一个小型原生模块中，更方便保持来源的一致性。

长按右键通过 bridge 的鼠标输入处理实现。首次达到阈值时，用 GetForegroundWindow 获取活动窗口，再读取标题和所属进程。辅助全局快捷键只由 bridge 的 RegisterHotKey 注册，避免 Electron 和 bridge 重复注册；注册失败反馈给用户。[RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey)、[GetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow)

长按右键不是键盘热键接口直接支持的能力。鼠标钩子回调必须快速返回，等待长按、截图和模型调用不能放在回调内；原右键菜单何时已经出现也取决于宿主应用，因此首轮必须先做交互实验。短按透传或补发、长按消费及右键拖动兼容需要一并验证。[LowLevelMouseProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)

## 6. 六个核心模块如何落地

### 6.1 快速唤起与连续语音

主要交互分为两个阶段：首次长按右键自动开始录音，保持按住期间持续录音，松开自动暂停；点击“继续录音”后直接进入手动模式，持续录音直至点击“暂停”。后续每次点击继续与暂停都沿用手动模式，右键释放不再改变录音状态。暂停时提供删除、继续录音、完成记录。

录音组件在应用常驻时预创建，但未触发时不保持麦克风流。用户触发后才申请音频流并开始录制；首次权限拒绝、设备丢失或系统麦克风关闭时显示失败状态，不伪装成正在录音。

首次按住形成首个音频段，后续每次点击继续录音形成新段，均通过 MediaRecorder 分块传给 worker 并写本地临时文件。首次松开或后续点击暂停时结束当前段并释放本应用音轨；所有音频段归入同一草稿。产品层叫暂停，底层结束当前段，以免仅调用 MediaRecorder.pause 后麦克风流仍然活跃。多段分别转写并按顺序组合，不能直接拼接独立音频容器的字节作为完整录音。[MediaRecorder.pause](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/pause)、[MediaStreamTrack.stop](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/stop)

点击完成时，等待所有音频段收尾并校验附件，再提交正式记录；此前只保留本地草稿。输入监听异常、锁屏、休眠或设备异常应优先禁止继续采集。为录音 renderer 配置后台节流策略；无法保证按键释放与系统停止采集物理上零延迟，需要实际测量并界定响应预算。

分块保存只能降低损失风险。单个 MediaRecorder 块不保证可播放；崩溃后的未完成录音可能需要修复且可能失败，未落盘尾部也可能丢失。应用重启后将这类记录标为“录音异常结束”，不承诺零丢失。[W3C 录音规范](https://www.w3.org/TR/mediastream-recording/)、[MDN dataavailable](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event)

### 6.2 情境快照

MVP 必须能获取的字段以能力分级定义：

| 线索 | 首版策略 |
| --- | --- |
| 应用、窗口标题、时间 | 按触发前保存的窗口身份读取；读取失败保存错误状态 |
| 画面 | 已开启截图时，针对该 HWND 捕获单窗口的一帧，并记录实际截图时间 |
| URL、文档路径 | 首版接受用户主动补充；不能从窗口标题推造 URL 或路径 |
| 选中文字 | 首版接受用户主动粘贴；不静默模拟 Ctrl+C 或持续读取剪贴板 |
| 当前任务 | 来自用户此前明确选择的任务，或录音中明确表达的任务候选；没有则为空 |
| 后续浏览变化 | 首版不自动跟踪；之后可加入用户主动补充快照 |

截图建议在 bridge 使用 Windows Graphics Capture 针对指定窗口创建捕获项，取一帧后释放会话。官方 CreateForWindow 支持按 HWND 定位窗口；实际兼容性仍需在目标 Windows 和应用组合上验证。[CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow)

受保护窗口、最小化状态或应用兼容性导致失败时，只保留语音和已获元数据，不自动改为全屏截图。排除应用应在启动截图之前判断。首次验证需要覆盖多屏与缩放比例，避免截图错位。

默认截图保存在本机供回看，不自动发给文字模型。以后增加 OCR 时，将 OCR 结果作为派生文字，允许识别错误并保留对应图片依据。

### 6.3 转写与 AI 整理

仅在用户点击“完成记录”且正式保存成功后执行一条简单、可重试的流水线；松开暂停不触发处理：

**临时草稿提交为正式记录 → ASR 转写 → 话题与联想整理 → 生成检索索引。**

ASR 选型要求：中文、中英夹杂、段级时间戳、可处理预期录音时长。用真实口语样本比较专有名词、停顿和长句识别效果，再选定供应商，不先绑定模型版本。

整理模型接收转写、用户补充原文、明确任务及允许发送的元数据，输出符合 JSON Schema 的草稿，主要字段建议为：

- title：建议标题。
- ideas：用户表达的主要想法，逐条关联转写片段。
- branches：不同话题分支，保留表达先后顺序。
- explicit_connections：用户明确表达的信息联系及依据。
- uncertainties：用户表达的不确定判断。
- open_questions：用户提出的问题与 AI 建议的问题，标明来源。
- task_reference：明确任务的引用；未知保持空值。

每条内容保存 evidence_segment_ids、source_ids 和 origin（用户表达／AI 推测／用户修订）。没有材料支持的“为什么重要”显示“当时未记录”。模型不能以截图或标题代替个人动机。

结构与引用校验只能减少错误，不能证明语义完全正确。产品必须支持展开原话、点击时间点回听、修改草稿；原始音频、原始转写、修订稿和不同版本摘要分别保存。

不需要复杂 Agent 编排。外部资料作为待分析数据，模型不执行资料中的指令，也不执行外部任务。

### 6.4 灵感事件与无分类管理

核心单位采用“灵感事件”：一次完成的记录包含多段原始表达、一个起始快照、零个或多个思路分支。续录默认保留首次来源，不自动截图覆盖起始情境。自动标题和标签不影响正式保存。

建议数据对象：

| 对象 | 保存内容 |
| --- | --- |
| events | ID、时间、状态、可选任务、用户标题 |
| sources | 应用、窗口、截图路径、采集时间、用户补充原文或链接 |
| recordings / segments | 音频路径、格式、时长、转写版本、分段起止时间 |
| annotations | 整理条目、证据引用、来源类型、用户修订、模型版本 |
| tasks / relations | 用户任务、事件与分支关系；AI 关联建议与已确认关系分开 |
| search_chunks / jobs | 检索文本、向量及其模型版本；处理步骤、重试和失败原因 |

SQLite 保存结构化数据；音频与截图保存于应用数据目录，以事件 ID 组织。由专用 worker 串行协调写入，附件完成写入后再关联到正式记录。数据库事务不会替外部媒体文件刷盘，需要明确文件写入、持久化确认和数据库提交的顺序；启动时检查未完成事件与孤立临时文件。

建议状态分别管理：会话状态（空闲／长按判定／首次准备／按住录音／暂停／手动准备／手动录音／丢弃／提交／已保存）、处理状态（待转写／待整理／可检索／失败）。首次准备校验右键仍按住，手动准备校验续录许可仍有效；删除或暂停均使过期启动回调失效。不能因为向量生成失败，就把已保存的正式记录标成保存失败。

### 6.5 模糊检索与情境回溯

第一版用两路检索，不直接将全部历史记录交给聊天模型：

1. **关键词路。** 对转写、用户补充内容、窗口标题、任务和当前有效摘要建立 SQLite FTS5 索引。中文先分词，查询与建库使用一致规则；可用 Intl.Segmenter 做起点并用真实语料验证。保留原文用于高亮，短词和专有名词提供字面匹配补充。
2. **语义路。** 以转写段落或思路分支为单位生成中英混合语义向量，存入 SQLite。少量个人记录先由 worker 计算余弦相似度；测出性能瓶颈后再引入专门的向量索引。
3. **合并。** 合并两路排名，按事件去重并聚合命中片段，再展示最相关记录。时间、任务和应用是可选筛选条件，不把查询中模糊的时间猜测强制作为过滤器。

FTS5 提供全文检索与 BM25 排序，语言切分仍需单独设计；Intl.Segmenter 提供按语言分词的基础能力。实际检索效果还需要结合样本评估。[SQLite FTS5](https://www.sqlite.org/fts5.html)、[Intl.Segmenter](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter)

结果卡默认包含：当时任务（如有）、自己说的原话、来源应用和日期、截图缩略图、AI 整理草稿、命中依据及原音频入口。先展示相关记录，不用一段生成回答替代证据。

如果增加“根据旧灵感回答当前问题”，使用 RAG（检索增强生成）：先从已完成记录中检索相关片段，再把片段与问题一起交给模型，生成附事件及原话引用的回答。当前的搜索列出相关记录，转写和单次整理各自处理一条表达；RAG 问答留待后续扩展。[RAG 原始论文](https://arxiv.org/abs/2005.11401)

网络不可用或未开启向量服务时，已保存的记录仍能浏览并进行本地关键词检索；语义能力明确显示不可用。首次检索不应等待全部历史索引重建。用户修订或删除记录后，同步更新关键词和向量索引，避免旧摘要继续影响检索。

### 6.6 思路主线与返回点

任务锚点只来自用户明确输入、选择或表达的内容。自动沿用的任务需要显示原始来源与时间，用户可以清空；没有任务锚点时，显示“任务未记录”，仅提供起始画面和来源窗口。

表达结束后，按顺序呈现“起始情境 → 提到的方向 → 尚未确定的联系”。不以模型判断“是否跑题”来纠正用户。

返回能力分级：

- **P0：** 回看截图、窗口标题和原始语音；原窗口仍在时，尝试切回。
- **P1：** 已可靠获取 URL 或文档路径时，打开来源。
- **P2：** 针对特定网页或应用恢复到消息、段落、页码或滚动位置。

HWND 只是临时窗口句柄，需结合 PID、进程启动身份等信息核验，不能作为长期唯一来源 ID。切回窗口也受 Windows 前台窗口策略限制；失败时保留手动入口，不用循环抢焦点。[SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)

## 7. 本地优先与云端处理

“本地保存”与“模型在本地运行”分别说明。建议第一版采用本地资料库加用户主动开启的云端模型 API，以降低部署难度。

| 功能 | 可能离开本机的数据 | 默认设计 |
| --- | --- | --- |
| 本地记录 | 无 | 音频、截图、元数据先临时保管，完成后正式保存；删除清理本次全部材料 |
| 云端 ASR | 当前已完成事件的音频 | 用户开启且点击完成后使用；未开启可保留录音 |
| 云端整理 | 转写、允许的任务和来源文字、必要元数据 | 单独明确范围；截图不自动发送 |
| 云端 Embedding | 需要索引的文字、当前搜索句子 | 明确说明；未开启时保留关键词检索 |
| 图片理解 | 截图或裁剪画面 | 不纳入首版默认调用 |

个人原型可采用用户自带 API Key，密钥由主进程使用操作系统保护机制保存，避免放入页面脚本、普通配置或日志。Electron safeStorage 在 Windows 使用 DPAPI，但不能据此承诺防御同一用户权限下的其他进程。[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)

临时草稿不得触发云端转写、整理、Embedding 或内容日志上报。这样用户在误触或表达中途选择删除时，数据仍限定在本应用的本地临时范围。

公开分发时若使用开发者的服务密钥，应增加受控服务端代理和额度管理，不能把共享密钥打包到客户端。此能力与首轮个人验证分阶段建设。

删除记录需要清理关联音频、截图、转写、摘要、关键词索引、向量和缓存；正在处理的任务应取消或检查删除标识，避免完成后把内容重新写回。用户主动导出的备份及外部模型服务留存需要单独说明，不能用一次数据库 DELETE 代表所有副本已消失。

## 8. 开发顺序与每阶段交付物

### 阶段一：桌面能力验证

交付一个不接云端模型的技术演示：首次长按右键录音与松开暂停、点击继续后的持续录音与手动暂停、起始截图与浮层、三个选项、同一草稿清理及本地播放。

覆盖浏览器、PDF 阅读器、聊天客户端和至少一种办公软件；检查普通右键、右键拖动、误触快速松开、迟到的截图与录音启动回调、删除后无内容复现、权限拒绝、多屏与缩放、设备丢失及截图失败。还需验证原生 bridge 与 SQLite 在打包后可运行。

此阶段若发现某类应用无法截图，定义支持范围和降级行为，不改为默认采集整个桌面。

### 阶段二：原始记录闭环

交付事件列表和详情、本地音频与截图、可选任务与来源补充、删除、异常结束记录提示。断网时也必须完成这一闭环。

### 阶段三：AI 处理与找回闭环

交付带时间段的转写、可追溯整理、修订、中文关键词和语义混合检索。用实际中文口语与几天后的模糊描述评测。

### 阶段四：真实使用验证

观察用户是否愿意捕捉、是否在数天后重访、是否能理解原始意图。根据结果决定优先增强来源文字、任务锚点还是检索，而不是直接扩建知识图谱。

后续再实现：浏览器扩展、选中文字适配、本地 OCR、精确位置返回、关联推荐、RAG 问答及本地模型。浏览器扩展仍须遵守按用户触发授权的访问边界，不自动获得全部网页历史。[Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)

## 9. 如何验证产品价值

当前证据仍来自单人自述，以下是建议研究设计。

- **捕捉是否足够低负担：** 在真实阅读中观察从用户表达记录意图到音频实际开始的时间、误触和放弃；日志不能统计那些没有触发工具的隐性放弃。
- **情境是否有帮助：** 比较“原文或链接＋个人想法”与“同类记录＋任务、截图和来源线索”。数天后让用户解释当时的联系。采用相近记录随机分组或平衡顺序，减少重复看同一条造成的记忆影响。
- **能否找回：** 让用户使用自然回忆描述搜索，记录首次有效结果、找到目标所需时间和失败原因，同时检查是否真正理解。
- **AI 是否忠实：** 将整理条目逐条对照原始录音，检查遗漏、张冠李戴、把猜测变事实以及无依据添加动机。
- **是否重新使用：** 收集用户把旧想法带入实际项目的具体案例，不以保存量或搜索点击量代替价值。

先记录基线，再制定阶段目标；此方案不预先宣称提升率、检索准确率或节省时间。

## 10. 一条示例记录

以下仅为演示数据。

**来源现场：** 用户在浏览器中阅读 AI 产品经理作品集，触发时保存窗口标题和当前画面。

**用户明确的任务：** 寻找适合 AI 应用产品经理求职的项目。

**用户语音：** “这里说作品集要解释产品取舍。我想到之前收藏了很多东西，但后来忘了为什么收藏。也许项目可以把收藏当时的理由留下来。今天还是先找项目方向。”

**整理草稿：**

- 方向一：作品集需要呈现产品取舍，引用对应原话。
- 方向二：探索保存收藏理由的工具，引用对应原话。
- 明确主线：今天先寻找项目方向，引用用户表达。
- 未确定：是否存在其他用户同样需要；这不是用户已经验证的结论。

几天后搜索“之前那个收藏了不知道为什么重要的项目”，结果卡展示原话、当时截图、任务和整理。即使用户判断这个方向已经不值得继续，系统也完成了帮助重新理解与判断的任务。
