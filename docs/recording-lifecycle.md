# InMoment 录音交互与数据生命周期

历史设计基线：v0.2｜原稿日期：2026-10-16｜状态注记更新：2026-10-17

依据：当时明确的交互要求——首次长按右键触发并按住录音，松开自动暂停；此后点击继续录音直接开始持续录音，无须按住右键，由用户手动点击暂停。暂停时提供删除、继续录音和完成记录三个选项。

这是早期设计稿。录音和草稿流程现已实现，当前操作见[使用指南](USER_GUIDE.md)，测试结果见[验证记录](validation.md)。

## 1. 产品规则

1. 未达到长按阈值，不截图、不启用麦克风、不创建内容草稿。阈值是待测试参数，不预先声称某个毫秒值最佳。
2. 首次达到阈值后才建立临时会话，在浮层出现前尝试捕获原活动窗口；不提前持续采集屏幕或音频。
3. 首次录音采用按住模式：右键仍处于有效按住状态才允许启动和持续录音，松开立即请求停止，不等待截图、写盘或模型任务。
4. 首次松开表示暂停，不自动判断为误触，也不自动完成记录。每次暂停均可选择删除、继续录音或完成记录。
5. 点击继续录音直接进入手动模式并启动下一段，向同一草稿追加音频；无须再次按住右键。点击暂停才暂停，后续继续与暂停均沿用手动模式。
6. 首次录音、手动续录和暂停阶段只保管本地草稿，不上传内容、不调用模型、不进入正式列表与检索索引。
7. 点击完成记录后，等待当前音频段及附件收尾，提交一条正式记录。用户已开启的 AI 能力此后才能执行。
8. 点击删除清理本次草稿的全部关联数据，不进入回收站；删除其他历史记录是独立操作。

## 2. 状态与转移

| 当前状态 | 事件 | 下一状态与动作 |
| --- | --- | --- |
| 空闲 | 右键按下 | 长按判定；仅处理输入和计时 |
| 长按判定 | 阈值前松开 | 返回空闲；无内容采集；恢复适配范围内的普通右键操作 |
| 长按判定 | 达到阈值且仍按住 | 创建本地草稿，记录原窗口，启动授权截图及音频准备 |
| 首次准备采集 | 麦克风就绪且仍按住 | 开始首次按住录音；显示真实录音状态 |
| 首次准备采集 | 右键已松开 | 禁止启动录音；已打开的音轨立即关闭；进入暂停 |
| 首次按住录音 | 右键松开 | 立即请求停止当前段并释放音轨；显示暂停菜单 |
| 暂停 | 点击继续录音 | 复用草稿 ID，进入手动准备采集；无须按住右键 |
| 手动准备采集 | 麦克风就绪且续录许可仍有效 | 直接开始手动录音 |
| 手动准备采集 | 点击暂停、删除或完成 | 撤销本次启动许可；迟到音轨关闭，不自动开录 |
| 手动录音 | 点击暂停 | 停止当前段并释放音轨；显示暂停菜单 |
| 手动准备采集或手动录音 | 右键按下或松开 | 不改变录音状态，不新建草稿；保留正常右键使用 |
| 暂停 | 点击删除 | 标记丢弃、撤销写入许可、取消任务并清理材料 |
| 暂停 | 点击完成记录 | 进入提交；完成持久化后成为一条正式记录 |
| 任一活动状态 | 输入监听异常、锁屏或录音设备异常 | 优先禁止继续采集，进入暂停或异常提示；不自动完成或上传 |

状态转移由事件驱动，与“是否说了足够多的话”“有没有声音”“AI 判断是否有价值”分离。静音与记录很短都不能直接证明误触。

达到阈值后快速松开时，仍进入暂停菜单；用户点删除即可取消。若录音未产生有效音频，完成操作需如实提示可保存哪些材料，不能伪造语音内容。

## 3. 截图时序

首次触发采用以下顺序：

**长按达阈值 → 冻结原窗口身份 → 开始授权截图与录音准备 → 截图完成、失败或超时 → 显示浮层或暂停菜单。**

首次按住模式下，右键释放的优先级高于截图完成。等待画面时也必须处理松开事件；首次录音启动回调返回时再次检查按住状态和会话版本。手动续录的启动回调检查会话与续录许可，不检查右键是否按住。

“在小球出现前采集”只描述 UI 显示顺序，不表示从过去取得画面。分别记录触发时间与实际截图时间，截图延迟可能产生画面变化。

截图失败不自动改截全屏。续录默认保留首次来源，不自动把暂停菜单、浮层或后来的窗口覆盖为起始情境。后续如增加“补充现场”，必须是用户明确发起的另一次采集。

## 4. 暂停与麦克风

产品层保留同一草稿，音频层首次按住形成首段，松开结束首段；点击继续录音形成后续段，点击暂停结束该段。每次暂停均释放本应用持有的音轨。所有段属于同一记录，不重复创建起始截图与来源。

仅调用 MediaRecorder.pause 会停止向录音块收集数据，但不等同释放音频流；不能据此承诺 Windows 麦克风使用指示立即消失。MediaStreamTrack.stop 用于结束本应用对音轨的使用；其他程序同时使用麦克风时，系统仍可能显示麦克风正在使用。[MediaRecorder.pause](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/pause)、[MediaStreamTrack.stop](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/stop)

每段正常结束后成为独立附件，保留段号、实际起止时间及有效录音时长。多段分别转写并按顺序组合，不将独立 WebM 文件直接作字节拼接。暂停时间不伪装成用户表达，但保留时间映射供回溯。

首次阶段的“松开立即暂停”和后续阶段的“点击暂停”都是交互要求。系统输入、IPC、设备与录音缓冲存在延迟，验收时分别测量两种停止方式的实际响应时间与尾音。

## 5. 删除的范围与顺序

用户选择删除时，清理属于本次草稿的：

- 起始截图、预览缩略图及任何派生图片。
- 全部音频段、音频块、播放器缓存和临时文件。
- 应用名、窗口标题、来源信息、用户补充文字和任务关联。
- 临时数据库记录、处理队列和内存中的引用。
- 若将来增加草稿内派生能力，还需清理派生文字和临时向量。

为避免删除后内容重新出现，执行顺序为：

1. 将会话置为丢弃并更新会话版本，撤销后续采集和写入许可。
2. 禁止创建新段，终止本应用音频流，取消截图与文件作业。
3. 所有异步结果在写入前检查会话 ID、版本及状态。迟到截图或音频结果直接丢弃；若底层已经写出文件，交给清理器删除。
4. 等待相关句柄释放，清理附件、缓存和临时元数据，核对没有残留作业。
5. 清理成功后才标记已丢弃。失败时持久化最少必要的清理任务并重试，不能静默显示全部已清除。

敏感截图、原话和标题不得出现在内容日志或崩溃上报中。取消期间保留的清理任务仅保存必要标识与路径，不建立可检索记录。

应用正常退出时，未完成草稿可提示用户选择完成或丢弃；意外崩溃留下的未决定草稿应与用户明确删除的草稿区分，不能自动提交或上传。已明确删除的内容只允许继续清理，不提供恢复入口。

应用内删除会清理本程序管理的数据，操作系统分页、用户备份和外部服务已收到的数据不在清理范围内。完成前资料保存在本机，丢弃草稿时直接在本地清理。

## 6. 长按右键的原生兼容性

低级鼠标钩子能够处理右键按下和释放，但应运行于专用输入线程，快速投递事件后返回。等待长按、截图、音频处理和网络请求不能放在钩子回调内。Windows 可能在回调超时时静默移除钩子。[LowLevelMouseProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)

原软件的右键行为需要单独决策与测试：透传原始事件可能同时打开菜单或触发右键拖动；先拦截再补发短按则改变原始事件时序，也可能被某些程序拒绝。不能承诺所有应用同时具备零干扰的普通右键与长按录音。

首轮建立明确的支持应用范围与排除选项，测试浏览器菜单、PDF 菜单、设计软件右键拖动及多显示器；保留可配置辅助入口，但不以辅助入口替换主要交互要求。

首次按住模式下，录音控制器使用按键状态与输入健康检查，出现不一致时优先停止采集，不能只依赖一次鼠标释放消息或浮层自身的鼠标事件。进入手动模式后，右键状态不再作为录音许可；仍处理控制进程失联、锁屏、设备异常等故障，但不能因用户松开右键而自动暂停。

## 7. 涉及的 AI 与软件技术

| 技术 | 在 InMoment 中的用途 |
| --- | --- |
| ASR | 完成后将音频转成文字，并保留段级时间依据 |
| LLM 结构化输出 | 将用户表达整理成想法、分支、明确联系和待验证问题 |
| Embedding | 用语义表示支持“记不清原话”的查询 |
| 混合检索 | 关键词与语义召回结合，覆盖专有名词和模糊描述 |
| RAG | 在检索到真实旧记录后，基于这些记录生成带引用的回顾或回答 |
| OCR／图片理解 | 后续用于从截图提取可搜索文字或理解画面；首版截图先用于回看 |
| 状态机与异步取消 | 保证按住、松开、删除、续录、完成等行为一致，防止迟到回调继续采集或写回 |
| Windows 输入与窗口 API | 全局右键识别、窗口身份、经授权的单窗口截图 |
| 本地存储与持久化作业 | 区分临时草稿、正式记录、取消清理和 AI 处理状态 |

RAG 是检索增强生成；只搜索并列出记录属于检索。单次转写整理不必使用 RAG，也不需要将用户资料用于模型训练。RAD 若指 Rapid Application Development，则是快速应用开发方法，和 RAG 是不同概念。[RAG 原始论文](https://arxiv.org/abs/2005.11401)

## 8. 交给 AI 开发的建议顺序

AI 辅助实现个人 MVP 是可行的开发路线判断，但原生交互、隐私与删除行为需要实际验证，不能用“代码生成了”代替完成验收。

1. 先做无云端模型的桌面技术演示：右键短按／长按、浮层、录音分段、暂停、删除、继续及完成。先解决最不确定的原生交互。
2. 实现本地草稿、正式记录及删除清理，用测试覆盖状态机和迟到回调；在真实 Windows 中验收输入和音频。
3. 接入 ASR 和结构化整理，确认只有完成后的材料会进入处理。
4. 实现关键词与语义检索；有真实记录和查询后，再决定 RAG 问答的呈现方式。
5. 用真实使用验证首次长按的误触、自动暂停，以及后续手动续录对长时间表达和边浏览边思考的影响。

需求交给 AI 时，应逐模块提供状态、输入输出和验收场景，每一阶段运行验证通过后再继续。

## 9. 关键验收案例

| 场景 | 预期行为 |
| --- | --- |
| 右键短按，未达阈值 | 适配范围内保留普通右键行为；无截图、录音、内容草稿和云端请求 |
| 小球出现后很快松开 | 停止当前段，显示三个选项；不自动删除或完成 |
| getUserMedia 尚未返回时松开 | 迟到音轨被关闭，不在释放后启动录音 |
| 暂停一分钟 | 无新增音频，不持续占用本应用音轨；无 AI 处理请求 |
| 点击继续录音但没有按住右键 | 直接持续录音，追加到原草稿；显示可点击的暂停按钮 |
| 手动录音时按下或松开右键 | 不暂停录音、不新建草稿；可正常使用右键 |
| 手动录音时点击暂停，再点击继续 | 暂停后停止采集；再次点击继续直接续录，始终沿用手动模式 |
| 手动开麦尚未返回时点击暂停 | 迟到音轨关闭，不在暂停后自行开始录音 |
| 截图尚未返回时删除 | 迟到结果不得复活文件；本次全部材料完成清理 |
| 删除时仍有音频写入 | 撤销写入许可并等待句柄释放，最终清理所有分段；失败可见并重试 |
| 首次按住阶段输入监听异常 | 优先停止录音，不继续假设用户仍在按住 |
| 重复点击完成或网络失败 | 只提交一条正式记录；原始资料保留；AI 作业可重试 |
| 正式记录搜索 | 不返回临时、已丢弃或已删除的内容 |
